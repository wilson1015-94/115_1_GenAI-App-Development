## 二、輸出欄位契約

外層必須是物件，且只能有下列三個欄位，三欄都要存在。`required` 表示欄位存在，不表示內容已經正確；程式另外檢查文字不能為空或全空白。

| 欄位名稱 | 型別／限制 | 用途 | 畫面標籤 | 如何查原文 |
|---|---|---|---|---|
| `title` | `string`；必填、非空白 | 用短標題呈現原文主題 | 標題 | 檢查標題是否符合原文主題，未加入原文沒有的活動或課程名稱。 |
| `summary` | `string`；必填、非空白 | 用兩三句話整理主要內容；不足時說明不足 | 摘要 | 逐句核對原文；日期、數字與規則須一致，未知資訊不能自行補齊。兩三句是任務規則，程式沒有自動計算句數。 |
| `key_points` | `array of string`；必填；可為 `[]`，既有項目須為非空白字串 | 將重點拆成便於閱讀的項目 | 重點 | 每一項都要找得到原文依據，不能把推測、建議或虛構待辦混入清單。 |

處理順序是：檢查拒答與完成狀態→確認回應非空→解析 JSON→`check_result` 檢查欄位與型別→保存原文與結果→顯示。
結果保存在 `st.session_state.record`，不等於寫入永久檔案；畫面同時顯示當筆原文，方便人工回查。

### 3-2 案例 A：正常資料

**完整虛構原文：**

> 今天的課堂介紹 Streamlit 表單與 session_state。表單內的輸入會在按下送出後一起提交。session_state 可以保存同一個使用階段中的資料，讓程式重跑時仍能顯示前一次結果。

**示例中記錄的API輸出（虛構）：**

```json
{
  "title": "Streamlit 表單與狀態保存",
  "summary": "本次課堂介紹 Streamlit 表單與 session_state。表單會在送出時集中提交輸入，session_state 則能在同一使用階段的程式重跑後保留資料與前次結果。",
  "key_points": [
    "表單輸入在按下送出後一起提交。",
    "session_state 可以保存同一使用階段的資料。",
    "程式重跑後仍可顯示前一次結果。"
  ]
}
```

人工核對填寫示例：標題對應主題；摘要與每項重點都能在原文找到依據，沒有新增日期、人物或待辦。因此這筆紀錄判定為可用，但不代表其他輸入也一定正確。

| API紀錄欄位 | 虛構填寫內容 |
|---|---|
| 測試日期 | 2026-11-03 14:20（臺灣時間） |
| 執行位置／模型 | Streamlit Community Cloud／`gpt-5.4-mini` |
| JSON／畫面結果 | 如上方JSON；畫面依序顯示「標題、摘要、重點」，並附本筆原文。 |
| 請求數／判定 | 1次，無重試；欄位檢查與逐欄人工核對通過。 |

### 3-3 案例 B：資訊不足

**完整虛構原文：**

> 筆記內容待補。

**示例中記錄的API輸出（虛構）：**

```json
{
  "title": "筆記內容待補",
  "summary": "原文只說明筆記內容待補。尚未提供課堂主題或實際內容，資訊不足，無法整理具體重點。",
  "key_points": []
}
```

人工核對示意：原文沒有日期、人物、課程名稱或具體重點；示意資料沒有補造上述內容。空清單的意思是未列出項目，不能因此把必填的 `key_points` 整欄刪除。

| API紀錄欄位 | 虛構填寫內容 |
|---|---|
| 測試日期 | 2026-11-03 14:25（臺灣時間） |
| 執行位置／模型 | Streamlit Community Cloud／`gpt-5.4-mini` |
| JSON／畫面結果 | 如上方JSON；摘要說明資訊不足，重點區顯示「原文沒有對應項目。」 |
| 請求數／判定 | 1次，無重試；沒有補造未知資訊，空清單合法，判定通過。 |

本虛構紀錄合計2次API：案例A一次、案例B一次。部署驗收沿用這兩筆，不另送出；空白、過長、缺key與離線模擬不計對外請求。
實作時仍須按真正送出的次數記錄；API預設關閉，啟用後每次有效提交最多1次、無自動重試，失敗也可能產生費用。

**反思填寫示意：**

- 最有用的欄位：`key_points` 將重點分開，方便逐項對照原文；`summary` 提供整體脈絡，兩者用途不同。
- 錯誤與處理（虛構）：第一次部署將requirements放在入口上層的中間資料夾，安裝時缺少python-dotenv；移到入口同層後Commit／Push，確認安裝紀錄與App啟動成功。這是示範如何記錄「問題→修正→再次確認」。
- 已知限制：只支援文字與文字清單；程式不驗證摘要是否真的兩三句，也不保證內容忠於原文。狀態保存不是永久存檔，`store=False` 仍會傳送原文到 API。
- 下一步（虛構填寫）：增加不同長度與不同主題的筆記案例，觀察是否遺漏重點；若要擴充文字檔上傳，先加入大小與編碼檢查，再測試狀態清除是否正確。
